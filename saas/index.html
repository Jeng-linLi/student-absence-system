2. Proposed Solution方案概述

SAAS is a single web + mobile platform covering three previously disconnected processes — absence requests, assessment conflict resolution, and official activity verification — behind one workflow engine, one notification bus, and one analytics layer. SAAS 以一套網頁 + 流動應用，統一承載三條原本割裂的業務線：請假申請、考評衝突處理、官方活動核實；共用同一工作流引擎、同一通知總線與同一分析層。

One submission一次提交

Student fills one form; SAAS resolves affected courses and assessments automatically and routes to the right approvers. 學生只填一次表；系統自動解析受影響課程與考評，並分派給正確審批人。

One workflow engine統一工作流引擎

Configurable, rule-driven approval chains (medical / official activity / long absence) with SLA timers and escalation. 規則驅動、可配置的審批鏈（病假／官方活動／長期請假），附 SLA 計時與升級機制。

One source of truth單一事實來源

Every action is logged; every document is versioned; every report is reproducible from the same ledger. 所有操作留痕、文件版本化、報表可從同一帳本重現。

6.2 Regulatory — PIPL / 個人資料保護法 exposure ends now6.2 法規 — 個人資料保護法風險即須收斂

Student absence data is personal information: health reasons, family events, accommodation needs. Today it lives in private email inboxes — uncontrolled retention, no deletion mechanism, no cross-border audit trail. Under the Personal Information Protection Law (PIPL) and HKUST(GZ)'s data-protection obligations this is a live compliance gap: every academic term it persists is another cohort's PII exposed outside the institution's governed perimeter. SAAS moves all of it into a single, retention-scheduled, access-controlled, audit-logged system aligned with FERPA / GDPR mapping (see Data & Security). 學生請假資料屬個人資訊——健康事由、家庭事件、便利需求。目前散落於私人電郵信箱：留存無控、刪除無機制、跨境無軌跡。依《個人資訊保護法》（PIPL）及港科大（廣州）資料保護義務，這是活生生的合規缺口——每多拖一個學年，就多一屆學生的個人資料暴露於校園治理邊界之外。SAAS 將全部資料收進單一、有留存期、有權限、有審計的系統，並對齊 FERPA / GDPR 對應（見「資料與安全」）。

This package ships a runnable prototype (leave-system/, v1.2.1, 105 unit tests + 183 smoke checks in CI) that the steering committee can try before approving: submit a request, walk it through two-level approval, watch the timetable-aware affected-course preview, inspect the audit log. The prototype already implements CSRF protection, attachment content-sniffing, transaction-safe email delivery, scope isolation and paginated account admin — the design package is not aspirational, it is a specification of what already runs. 多數企業級提案只憑介面稿就要預算。本提案附帶可執行原型（leave-system/，v1.2.1，CI 內 105 項單元測試 + 183 項冒煙檢查）——指導委員可在核准前先試用：提交假單、走完兩級審批、查看課表感知的受影響課程預覽、檢視稽核日誌。原型已實作 CSRF 防護、附件內容嗅探、交易安全郵件投遞、範圍隔離與帳號管理分頁——設計提案不是空想，而是對「已經在跑的系統」的規格說明。

Bottom line（結論）: DingTalk and Feishu can handle "student submits form → teacher clicks approve." They cannot handle "student submits form → system resolves 6 affected courses → detects 2 assessment conflicts → routes to advisor then faculty → advisor picks make-up date → student gets calendar invite → audit log captures everything → registry sees trend dashboard." That multi-step, domain-specific flow is what SAAS automates — and it is why bolting absence management onto a general-purpose IM tool costs more in workarounds than building the right system. 結論：釘釘與飛書能做「學生填表 → 教師點核准」。做不了「學生填表 → 系統解析 6 門受影響課程 → 偵測 2 個考評衝突 → 分派導師再院系 → 導師選補考日期 → 學生收行事曆邀請 → 審計日誌全程留痕 → 教務處看趨勢看板」。這條多步驟、領域專用的流程就是 SAAS 自動化的核心——也是為什麼把請假管理硬塞到通用通訊工具上，繞路成本比建正確系統更高。
